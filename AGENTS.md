# myLFR Desktop contributor guide

- Product: local-first Windows desktop application for a single LFR business per installation.
- Stack: React 19 + TypeScript + Vite frontend; Tauri 2 + Rust + SQLite backend.
- Runtime data must remain local. Do not add Supabase, authentication, analytics, telemetry, or generic SQL execution from the webview.
- Node baseline is 22. Run `nvm use` before npm commands.
- The webview calls only typed commands defined in `src/lib/desktop.ts`; Rust validates again at the trust boundary.
- Store monetary/weight-like decimal values as scaled integers. Greenweight is centi-kilograms.
- All landing saves and deletes must remain transactional and create immutable revisions.
- The bundled fishstock catalogue is frozen: it seeds new databases only, and an application update must never apply a catalogue to an existing database, because that would switch off the stocks receivers added. Receivers maintain additions themselves; official stocks are read-only. Never delete a fishstock code a landing uses.
- Fishstock codes are classified into three fishing years. Before changing that classification, read `docs/fishing-year-rules.md`; a prefix match that captures the wrong stock silently misreports a receiver's totals.
- Backup restore must validate checksums and database integrity before replacing live data.
- Database compatibility is tracked separately from the app version. Before changing persisted SQLite structure or data rules, read `docs/database-versioning.md`. Add an append-only numbered migration to `src-tauri/src/db.rs`, set `PRAGMA user_version` to that migration's exact number, and update the migration/backup compatibility tests. Never edit an old migration or use a future schema number as an earlier migration's completion marker.
- A newer app must migrate every supported older schema forward; an older app must reject a newer schema. Backup compatibility is based on backup format and schema version, not an exact app-version match. Keep the schema migration matrix and failed-migration safety test passing.
- Record proposed, planned, and in-progress product capabilities in `FEATURES.md`. Once implemented and verified, move them to the `Implemented workflows` section of `README.md`.
- Build Windows releases in Windows CI. Public releases are distributed without Authenticode (decided 2026-11-15; see `Distribute the Windows installer unsigned` in `FEATURES.md`), so the Tauri updater signature is the required signature for every release and update. Never publish a build signed with the self-signed pilot certificate. A signed build pins its Authenticode publisher; only an explicit `MYLFR_UNSIGNED_WINDOWS_RELEASE=1` build may skip that check.
- Development uses two checkouts intentionally: the main WSL checkout and a Windows checkout of the same repository. Their locations are in the maintainer's local agent memory, not in this repository. Keep code changes in one checkout at a time, push or commit them, and pull them into the other before testing; do not edit both copies simultaneously. The Windows checkout exists so the app can be run with the native Windows toolchain and WebView2, which is the rendering engine used by receivers.
- To run the WebView2 development app, open PowerShell in the Windows checkout, run `nvm use` when Windows nvm is installed, verify `node --version` is 22.x, install dependencies once with `npm ci --ignore-scripts`, then run `npm run desktop:dev`. This opens the Tauri window using WebView2. Do not open `http://localhost:1420` in a normal browser and treat it as the app: that address is only Vite's frontend server and does not provide the Tauri/Rust bridge. The current Windows machine uses a system Node 22.19.0 installation and does not have Windows nvm, so its existing Node version must be checked instead.
- Before calling a change verified, check which levels it needs in `docs/testing.md`, and report which were run. Passing tests prove behaviour, not appearance.
- In explanatory text anywhere in the app (dialogs, FAQ, help, warnings, and notifications), render button references in bold using the button's on-screen wording. Use `<strong>` in JSX or `**label**` in text rendered by `RichText`; never display raw Markdown markers in native dialogs or input validation messages.
- Use the native Windows Tauri window for accurate live layout checks. Use an installed Windows build and the packaged smoke test for final visual and release verification. The WSL/Linux Tauri window uses WebKitGTK and remains useful for functional checks and fast iteration, but it is not visual evidence for the Windows product. The two development checkouts also have separate development databases.
- `docs/overnight-queue.md` holds work an agent may complete unattended, with the standing rules for such a run. It is a queue, not a history: finished tasks are deleted, and a single `Last run` section, replaced each run and appended to as each task finishes, carries the summary. Unattended runs branch per task and never commit or push to `main`. A task belongs there only if its acceptance check is a command that passes or fails; the exclusion list in that file is absolute.
- Licence: the project is dedicated to the public domain under CC0 1.0 (`LICENSE`, SPDX `CC0-1.0`). The author has renounced ownership; this is a settled decision, not open for review. Do not switch to another licence, and do not add copyright notices, author attributions, or "Copyright ©" lines anywhere; refer to the "maintainer", never the "owner". Only add material the author created, since CC0 cannot waive rights in third-party work; third-party dependencies keep their own licences.
- Bug reports go to the public GitHub issue tracker (`Magnifica101/myLFR-desktop`), and the app surfaces this in Settings → Bug report. There is no support email; do not add one. Security vulnerabilities go only through GitHub private vulnerability reporting as described in `SECURITY.md`, never a public issue. Never ask a user for their database or a backup; ask for the sanitized problem report.
- Outside code changes are not accepted. Bug reports are; pull requests from outside the project are closed without review (`CONTRIBUTING.md`). Do not add contribution guides, "good first issue" labels, or anything else that invites outside code.
- Before release, signing, installation, backup/restore, or packaged smoke work, read `HANDOFF.md`. Follow its controlled-attempt protocol: no more than three attempts for one task, document each failure before retrying, and stop immediately for any critical signing, publication, secret, database-integrity, or rollback-safety failure.
